## An Empty Initial Render

The NextJS version looked fine once it loaded, but the problem was around that initial render.

The root layout utilised separate desktop and mobile trees with a `useMediaQuery` hook. A `null` value was returned until React had mounted, which caused zero content rendering on the server side (validated in-browser by disabling JavaScript, resulting in a metadata shell + client rendering instructions).

<Alert variant="error" title="Issues caused by this">

- Web crawlers and link preview bots scanned the server-rendered HTML and received nothing aside from the metadata. This made link previews and indexable content useless.
- Poor UX for users in slow network zones and/or restricted environments. Because JS takes much longer to load, those devices would be stuck with a persistent loading state.

</Alert>

It's important to clarify that this isn't a shortcoming of NextJS. It is simply an app-first framework that I was using for a content-first site. I had the option of altering the `next.config.ts` file to export the site as static, but this would have added a lot more boilerplate and refactoring across the client component architecture and outputs.

## Redesigning the Site

This exploration began because I wanted to redesign my site to be more interesting and playful. The plan was to include animations across a background grid along with cleaner image transitions.

Using the old stack of React, NextJS and `motion/react` would have made this relatively simple to build. The grid could exist as a client component managed by hooks like `useEffect` and `useMotionValue`. However, the hydration and build time for 40+ purely decorative assets would have led to a huge bundle size relative to other frameworks.

## Why Astro Made Sense

Astro is a content-first framework that provides static HTML outputs, decoupling content from the interaction layer. Any additional JavaScript required is treated as an enhancement instead of a necessity.

I would be sacrificing the simplicity of lifecycle management with React, along with image storage in the form of Vercel Blob (integrated with NextJS). However, I chose to prioritise the easier mental model and smaller dependency surface provided by Astro.

Replacing Vercel Blob with an in-repo image store was also surprisingly more efficient:

## Takeaways

Sanity-check your SSR through the browser:

1. Right-click, go to 'View Page Source' and search for the main sections to verify the actual server contents.
2. Within the DevTools panel, disable JavaScript and reload the page.
3. Inspect the initial document response in the Network tab.

If none of these render any content, your site is likely relying entirely on hydration.
